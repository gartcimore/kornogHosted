# Plan: shared Valkey guest and Infisical

Status: **shelved 2026-11-19, not started.** Decision: no need for a secrets manager for now, so neither the Valkey guest nor Infisical will be built. Nothing here is built or applied. The plan is kept so the work can resume if the need comes back.

What already exists and stays as it is: the `infisical` role and database on the `db` guest (harmless, empty, no network client allowed), and its password in `postgres/db-passwords.env.secret`. Remove both from `ansible/host_vars/db.yml` and the secrets file only if you want the guest to carry nothing unused. `valkey/` and `infisical/` in the repo are old, never deployed files.

## Goal

A place to keep secrets for the other services (database passwords, API keys, VPN keys) with a web UI and an audit log: **Infisical**, self-hosted. It needs PostgreSQL (done: guest `db`) and Redis. Valkey is meant to be a shared backend for other future services too, so it gets its own guest, like `db`.

## What Infisical needs (official documentation, read 2026-11-18)

Sources: [requirements](https://infisical.com/docs/self-hosting/configuration/requirements), [environment variables](https://infisical.com/docs/self-hosting/configuration/envars), [Docker Compose deployment](https://infisical.com/docs/self-hosting/deployment-options/docker-compose).

- **The app:** the `infisical/infisical` container, stateless, listens on port 8080 (`HOST=0.0.0.0` to be reachable). Documented size per instance: 2 cores and 4 GB RAM (the Docker Compose page asks 4 GB and 2 cores for app, Postgres and Redis together). The old compose file in `infisical/` caps it at 256 MB: never deployed, far too low.
- **PostgreSQL:** the only supported database, 16 is the tested version, 14 or newer recommended. Our `db` guest runs 17. The role `infisical` and its database exist. Still missing: the address of the machine running Infisical in `clients` of `ansible/host_vars/db.yml`.
- **Redis:** required and persistent. It holds the job queue, locks and scheduled-job state. Redis 6.x or 7.x (at least 6.2). Eviction policy must be `noeviction`. Persistence on (AOF or RDB) and included in backups, because pending jobs live there. **Valkey is not named in the documentation: compatibility must be tested.**
- **Required environment variables:** `ENCRYPTION_KEY` (16 random bytes in hex, `openssl rand -hex 16`), `AUTH_SECRET` (32 random bytes in base64, `openssl rand -base64 32`), `DB_CONNECTION_URI`, `REDIS_URL`, `SITE_URL` (absolute URL with protocol).
- **Email (SMTP):** probably needed for invites and password resets. There is no mail relay. Left out for now, what breaks without it is not verified.

## Design notes

- **Valkey security.** There is no per-address rule list like `pg_hba`. Use TLS with the wildcard certificate (same copy and refresh design as `db`, including the early expiry warning), one ACL user per service with its own password, `noeviction`, AOF persistence, protected mode, bind to the LAN address. A firewall in front is part of the hardening plan.
- **Valkey with Infisical.** Test before relying on it: run Infisical against a throwaway Valkey and Postgres locally and look at startup, the status endpoint and the job queue. If it fails, use Redis (check what Debian 13 packages).
- **Secrets of the stack** (`ENCRYPTION_KEY`, `AUTH_SECRET`, Valkey password): generated by a script that never prints them, encrypted with git-secret like `arr/.env`. Treat `ENCRYPTION_KEY` and `AUTH_SECRET` as irreplaceable: what exactly is lost without them was not verified, keep an offline copy.
- **Backups.** Infisical's data is in Postgres: covered by the nightly dumps to Ymir and the guest backup. Valkey: the nightly guest backup, plus a documented restore.
- **What depends on it.** The repo handles secrets with git-secret and Ansible, which works without a running service. Do not make boot-critical services depend on Infisical at first. Its own secrets cannot live in it. Start with a few non-critical secrets.
- **Resources.** The host reports 12.7 GB (the iGPU reserves 3 GB), real use is about 2.5 GB. Limits proposed: valkey about 512 MB to 1 GB, infisical 3 to 4 GB, `db` 2 GB. These are ceilings, not reservations.
- **Order of work.** The two Postgres follow-ups (early certificate warning, time zone) are built first so the Valkey role can reuse the final certificate-refresh design. Then Valkey, then Infisical, then add its address to `clients`.
